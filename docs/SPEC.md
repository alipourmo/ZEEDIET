# ZeeDiet Clinic Management System — Build Specification for AI Coding Agents

Audience: Claude Code / Codex. Format: executable spec. Version 1.0 of this document. Written in English for the agent; every user-facing string in the product is Persian (RTL).

## 0. Agent Protocol (read first)

1. Read this entire document before writing code. Build strictly in sprint order (section 12). Do not start a sprint until the previous sprint's acceptance tests pass.
2. Work task by task. Each task has an ID (e.g. S2-T3). After each task: run the full test suite, run the linter, commit with message `S2-T3: <summary>`.
3. Do not implement anything outside the current sprint scope. Park ideas in docs/BACKLOG.md.
4. If the spec is ambiguous, pick the stated default, record it in docs/DECISIONS.md (date, question, choice, reason) and continue. Stop and ask the human only for questions marked BLOCKING in section 17.
5. Never hard-code Persian text in templates or code. All UI strings live in lang/fa/*.php and are referenced with `__('group.key')`. Code, identifiers, comments, commit messages, migrations and docs are English.
6. Never invent medical content. No diet advice, calorie targets or clinical thresholds are generated by the system in MVP; it only stores and displays what staff enter.
7. Never log or print secrets, OTP codes, passwords or full medical payloads in application logs.
8. Keep README.md current: setup, env vars, how to run tests, how to seed, how to deploy.
9. Every sprint ends with: migrations run on a fresh DB, seeders run, tests green, a short docs/sprints/S<N>.md note listing what was built and any deviations.

## 1. Product Summary

A single web application for a nutrition and weight-loss clinic (brand: ZeeDiet, Rafsanjan, Iran) with four role-based areas on one database:

| Area | URL prefix | Users |
|---|---|---|
| Admin and front desk | `/admin` | admin, secretary |
| Device operator | `/operator` | operator |
| Nutrition specialist | `/specialist` | specialist |
| Client portal | `/my-account` | clients (OTP login) |

Core loop: secretary books an appointment → operator records the device session and body measurements → specialist reviews, approves and publishes the report → client sees the published report and chart in the portal → SMS notifies the client at each step.

Primary goals: reduce front-desk errors, give every client a digital file with a progress chart, and give the manager operational visibility.

Conventions:
- Controllers thin; all rules in Services. Every write goes through a FormRequest.
- Every model uses explicit `$fillable`. `$guarded = []` is forbidden.
- Every query returning client data from a staff panel passes through a Policy or a scoped query; no raw `Client::all()` in views.
- Route names: `admin.clients.index`, `operator.today`, `specialist.reviews.index`, `portal.dashboard`.
- Migrations are append-only after a sprint closes; fix forward with new migrations.
- Soft deletes on clients; hard deletes are forbidden for all medical and financial tables.

## 7. Business Rules (implement in Services, cover with unit tests)

### 7.1 Availability and conflict detection

`AvailabilityService::isFree(resource, start, end, ignoreAppointmentId = null)` returns false when any of these is true:
- the date is in holidays or its weekday is in `config('clinic.weekend_days')`;
- the interval is not fully inside a schedules row for that resource and weekday;
- another appointment for the same device, specialist or room overlaps [start, end) and its status is not cancelled or no_show.

Overlap test: `existing.starts_at < new.ends_at AND existing.ends_at > new.starts_at`.

`BookingService::book()` must run inside a DB transaction that locks the relevant rows (`SELECT ... FOR UPDATE` on overlapping appointments of the same resources) so two simultaneous bookings cannot both succeed. Add a feature test that fires two competing requests.

A client may not have two overlapping appointments at the same time either.

### 7.2 Appointment lifecycle

Allowed transitions (anything else is rejected with a validation error):

- scheduled → confirmed | arrived | cancelled | no_show
- confirmed → arrived | cancelled | no_show
- arrived → in_progress | cancelled
- in_progress → completed

Every transition writes appointment_status_history and an audit log. Cancelling requires cancel_reason. Rescheduling is a transition-free update of starts_at/ends_at/resources that re-runs availability checks, writes an audit entry with old and new times and queues the appointment_rescheduled SMS.

### 7.3 Device session recording

`SessionRecorder::record()`:

1. Requires an appointment of the day (or an explicit "walk-in" flag allowed only for admin/specialist) in status arrived or in_progress.
2. Loads the client's device_contraindications and the device's contraindications. If the intersection is non-empty, return a blocking warning: the operator must tick an override checkbox and type a reason; the override is stored in device_sessions.parameters.override and written to the audit log. Admin and specialist can override; operator can only record after a specialist or admin has recorded an override acknowledgement for that client+device (store as settings key `override:{client}:{device}` with expiry) — default simplification for MVP: operators cannot override; the session is refused and the operator is told to contact the specialist.
3. Computes session_number as max(session_number) + 1 for the same client and device inside a transaction.
4. Links package_id automatically to the oldest package of the same service that still has remaining sessions; if none, the session is saved with package_id = null and flagged "no package" in the UI.
5. Moves the appointment to completed when the operator presses "finish".

Remaining sessions are always computed (see 6.3).

### 7.4 Measurement and report workflow

```
[operator or specialist records measurement_set]
      -> status = pending_review
[specialist reviews: may edit values]
      -> publish: status = published, reviewed_by, published_at
      -> SMS "report_ready" to client
[client portal shows only status = published and superseded_at IS NULL]
```

- A specialist recording a set may publish it in one step.
- A published set is immutable. A correction creates a new set with supersedes_id and status = pending_review; when published, the old row gets superseded_at.
- Charts and "latest values" use sets where status = published and superseded_at IS NULL, ordered by measured_at.
- Change summary (portal and specialist): first published value vs latest published value per measurement type; delta = latest − first, shown with sign.
- Validation ranges (reject, do not clamp): weight 20–400 kg, circumferences 10–300 cm, percentages 1–70. Values outside range return a validation error that the user can only override by an admin.

### 7.5 Client portal authentication (OTP)

- POST /my-account/login with mobile → always responds with the same message whether or not the mobile exists (no user enumeration). If a client exists, generate a 5-digit numeric code, store Hash::make(code), expire after 3 minutes, send via SMS template `otp`.
- Limits: max 3 code requests per mobile per 10 minutes and max 10 per IP per hour; max 5 wrong attempts per code, then invalidate it.
- Verify → log in with the client guard, regenerate the session, write an audit entry. Session lifetime 30 days idle 24 hours.
- Codes are never logged. In local and testing, LogGateway writes messages to storage/logs/sms.log for developer convenience; this file must be absent in production config.

### 7.6 Staff authentication

Mobile + password, rate-limited (5 attempts per minute per mobile+IP). Passwords minimum 10 characters. Admin can reset a user's password and deactivate users. Deactivated users are logged out on next request. Force password change on first login for seeded accounts.

### 7.7 Medical alerts

`medical.view_alerts` exposes only a computed badge set for any client card: allergy present (yes/no, text of the allergy list is shown only to roles with `medical.view`), contraindication keys, pregnancy status. Secretary and operator screens render these badges; they never render the free-text medical fields.

### 7.8 Audit logging

`AuditLogger::log(action, subject, clientId, changes)` is called by: login/logout (staff and client), any view of client_medical, any create/update of clients, medical data, appointments, sessions, measurements, payments, publish of a report, any password reset, any export. A model observer must not be the only mechanism (observers miss bulk updates); services call the logger explicitly and tests assert the entries. Admin UI at /admin/audit with filters (actor, client, action, date range) and pagination 50.

### 7.9 Normalization helpers

`Digits::toAscii($string)` converts Persian (۰۹) and Arabic-Indic (٠٩) digits and normalizes Arabic ي/ك to Persian ی/ک for all text inputs used in search or unique fields. Mobile normalization: strip spaces and +98/0098 prefixes, ensure 09xxxxxxxxx, reject otherwise. Apply in a middleware for all POST/PUT/PATCH and for search query strings.

## 9. SMS and Notification Events

Events dispatch queued jobs through `SmsDispatcher`, which renders the active template, writes sms_log as `queued`, calls the gateway, then updates status. Failed sends retry 3 times with backoff 1, 5, 15 minutes. Duplicate sends for the same (template_key, related_type, related_id) within 10 minutes are suppressed.

| Template key | Trigger | Default text (Persian, editable) |
|---|---|---|
| otp | OTP request | کد ورود شما به پنل {clinic}: {code} |
| appointment_confirmed | appointment created | {name} عزیز، نوبت شما برای {service} در تاریخ {date} ساعت {time} ثبت شد. {clinic} |
| appointment_reminder | scheduler, reminder_hours_before (default 24) | {name} عزیز، یادآوری نوبت {service} فردا ساعت {time}. {clinic} |
| appointment_rescheduled | reschedule | {name} عزیز، نوبت شما به {date} ساعت {time} منتقل شد. {clinic} |
| appointment_cancelled | cancel | {name} عزیز، نوبت شما لغو شد. برای نوبت جدید با ما تماس بگیرید. {clinic} |
| report_ready | report published | {name} عزیز، گزارش شما آماده مشاهده است. {clinic} |
| welcome | optional on client creation | {name} عزیز، به {clinic} خوش آمدید. پرونده شما ایجاد شد. |

Scheduler: `appointments:send-reminders` runs every 15 minutes and selects appointments with status scheduled or confirmed whose starts_at is within [now + reminder_hours_before, +15 min) and that have no appointment_reminder log entry. Quiet hours: do not send marketing-type messages between 21:00 and 08:00 (reminders and OTP are exempt).

SMS bodies must not contain diagnosis, weight or any medical detail.

## 10. Security and Privacy Requirements (acceptance-tested)

1. HTTPS only; `APP_ENV=production` forces secure cookies, HSTS, SameSite=Lax, HttpOnly.
2. CSRF protection on all state-changing routes; no GET routes change state.
3. Output escaped by default; any `{!! !!}` requires a code-review comment and a test.
4. Mass assignment protection via explicit `$fillable`; FormRequests whitelist fields.
5. Authorization: every controller action calls `authorize()` or is covered by route middleware `can:`; a test enumerates all named routes and asserts that each is either public (explicit allowlist) or protected. Add negative tests: each role against each forbidden route returns 403; cross-client access in the portal returns 404.
6. Uploaded files (from V1.0): stored on a private disk, served through an authorized controller with short-lived signed URLs, mime sniffing and size limits (10 MB, jpg/png/pdf).
7. Passwords hashed (bcrypt cost 12); OTP hashed; no secrets in logs; `.env` never committed; `.env.example` complete.
8. Backups: nightly mysqldump + `storage/app/private` archive, encrypted with a key from env, retained 14 daily and 8 weekly copies, stored off-server (configurable disk). Provide `php artisan backup:run` and `php artisan backup:restore-test` that restores into a temporary schema and verifies row counts. Document in README.
9. Consent: the client form has two checkboxes (data storage, photo storage); data-storage consent is required to save a client. Timestamp stored.
10. Data retention and deletion: no UI hard delete. client.delete soft-deletes; a documented artisan command `clients:purge {id}` (admin-confirmed, writes an audit entry) hard-deletes after the retention period set by the clinic.
11. HTTP security headers via middleware: `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, a restrictive CSP (self only, fonts and scripts from public/vendor).
12. Robots: noindex on every route of this app; robots.txt disallow all.

## 16. Deployment
